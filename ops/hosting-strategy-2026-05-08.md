# Hosting & Deployment Strategy
## Private Space Program — Analytical Infrastructure

Prepared by: Leke (Dev)
Date: 8 May 2026
Status: Awaiting founder approval before implementation

## Overview

This document lays out the full hosting and deployment architecture for the space
program's analytical infrastructure  covering the orchestration system, the study
site that external audiences will see, the CI/CD pipeline, and the demonstration
event environment. It covers what we have today, what needs to be built, and what
I recommend at each layer with honest cost figures and clear justification for
every decision.

The short version: the orchestration engine stays local by design. The study site
is already built and just needs correct deployment. The demonstration event
environment deserves a premium setup  clean domain, fast CDN, professional
presentation — because the people in that room will judge the organisation
partly by what they see on screen.

---

## 1. What the system actually consists of

Before making hosting decisions it is worth being precise about what each part
of the system is and what it needs from infrastructure.

**The orchestration engine** is the AI agent pipeline  the part that runs study
cycles, dispatches agents, enforces gates, and generates handbacks. This lives
in `system/orchestration/` and `system/tools/` and runs inside Claude Code on
the operator's local machine. It is a command-line tool, not a web service. It
talks to the Anthropic API directly. It reads and writes files in the repo. There
is no reason to put this on a server  doing so would add complexity, latency,
and cost with no benefit whatsoever.

**The study site** is the public-facing output  the HTML site that external
audiences, partners, and event attendees will see. It is generated by
`system/tools/build_site.py`, which takes the study's markdown content and
renders it into a clean, navigable HTML site. The rendered site for the completed
lunar pathfinder study already exists in the repo at
`studies/archive/lunar-humanoid-pathfinder/site/` — it is built and ready to
serve right now. When the spaceport study completes, `build_site.py` will
generate the same for that study.

**The CI/CD pipeline** is the automated quality check system — GitHub Actions
runs linting, schema validation, and the test suite on every push. This ensures
that no broken code or invalid data reaches the main branch. It is already
configured in `.github/workflows/ci.yaml`.

**The demonstration event environment** is a separate concern from day-to-day
deployment. It needs to be polished, fast, reliable, and professionally branded —
because the people in the room will be senior aerospace executives and investors
making judgments about this organisation's credibility.

## 2. Orchestration Engine: Local Execution via Claude Code

**Recommendation: Keep as-is. No server infrastructure needed.**

The orchestration engine is correctly architected for local execution. Claude Code
is the runtime. The Anthropic API handles the AI workload. The operator's machine
handles everything else. This is not a limitation — it is the right design for
a system that runs intensive analytical cycles that take minutes to hours, not
milliseconds.

Putting the orchestration engine on a server would require managing a persistent
process, handling Claude Code's session model in a server context, dealing with
file system state across deployments, and paying for compute that sits idle
between study cycles. None of that makes sense at this stage of the program.

The only infrastructure dependency here is a reliable machine with Claude Code
installed and an active Anthropic API key. That is already satisfied.

**Environment variable required:**
```
ANTHROPIC_API_KEY=<key>
```

Everything else the system needs is in the repo.

## 3. Study Site: Professional Deployment on Vercel Pro

**Recommendation: Vercel Pro with custom domain. Estimated cost: $20/month
plus domain registration (~$15/year).**

### Why Vercel

The study site is a static HTML site — pre-built by `build_site.py` and committed
to the repo. Vercel is the industry standard for serving exactly this kind of site.
It provides a global CDN, instant cache invalidation on deploy, branch preview
environments, and a clean deployment workflow that connects directly to GitHub.
The founder will have already seen Vercel deployments from this repo — there are
311 of them recorded in the GitHub deployment history, connected to this
repository already.

### Why Pro, not Hobby

The Hobby plan is free and works fine for development and internal previews. For
the demonstration event and for any external audience  partners, potential
contracted study clients, journalists, investors  we need the Pro plan. The
reasons are practical:

- **Custom domain with SSL** — `studies.[programname].com` instead of a Vercel
  subdomain. This matters for credibility. A senior aerospace executive clicking
  a link to `hello-world-gilt-ten.vercel.app` will notice. A link to
  `studies.spaceprograminc.com` reads as a professional organisation.
- **Password protection on preview deployments** — keeps in-progress study
  content private until it is ready to be seen externally.
- **Analytics** — understand who is looking at the study site, from where, and
  for how long. Useful intelligence before and after the demonstration event.
- **99.99% uptime SLA** — for a demonstration event, we need the site to be
  reliable on the night. Hobby has no SLA.

The Pro plan is $20/month. For an organisation operating at this level, that is
a rounding error.

### What needs to be configured

The Vercel connection to this repository already exists. What needs to happen is
correct configuration so it serves the space program study site rather than
the legacy content it is currently pointing at.

**Step 1 — Add `vercel.json` to the repo root:**

This file tells Vercel exactly where the built site lives and how to serve it.

```json
{
  "outputDirectory": "studies/archive/lunar-humanoid-pathfinder/site",
  "buildCommand": "",
  "installCommand": "",
  "framework": null
}
```

No build command is needed because `build_site.py` is run locally and the output
is committed to the repo. Vercel simply serves what is already there.

When the spaceport study completes, this file gets one line changed:
```json
{
  "outputDirectory": "studies/archive/01-orbital-platform/site"
}
```
That is the entire migration from one study to the next. One line. One deployment.

**Step 2 — Set the production branch in the Vercel dashboard:**

Change the production branch from `master` to `claude/setup-study-scaffolding-GYFFu`
(the active space program branch). This ensures the live site reflects the actual
study content, not the legacy code.

**Step 3 — Register a custom domain:**

Choose a domain that reflects the programme. Suggestions:
- `studies.[programname].com` — positions the site as a serious publication venue
- `research.[programname].com` — emphasises the analytical nature of the work
- `[programname]-studies.com` — if the main domain is already taken

Domain registration is typically $10–15/year through Cloudflare Registrar
(recommended  no markup, straightforward DNS management) or Namecheap.
Connect it to Vercel in the dashboard  Vercel handles SSL automatically.

**Step 4 — Enable password protection on preview deployments:**

Any push to a non-production branch creates a preview deployment. These should
be password-protected so in-progress study content is not publicly accessible.
Configure this in the Vercel project settings under the Environment tab.

## 4. CI/CD Pipeline: GitHub Actions

**Recommendation: Fix the one failing check. No other changes needed.**

The CI pipeline is already well-configured. Three jobs run on every push:
linting (ruff), schema validation (`validate_all_yaml.py`), and the test suite
(pytest). This is the right setup for a codebase where data integrity matters as
much as code quality.

There is one issue: the schema validation job currently fails on a pre-existing
data error in the archived lunar study. This causes every CI run to show a
failing check — which means the team has learned to ignore red CI checks. That
is a dangerous habit. A CI check that always fails teaches people to stop
looking at CI.

**The fix is one line.** The file
`studies/archive/lunar-humanoid-pathfinder/assumption_registry.yaml` is missing
a required `entries` field. Adding `entries: []` resolves the validation error
and makes the CI status meaningful again.

After this fix, a red CI check will always mean a real problem. That is the
standard we should hold.

## 5. Demonstration Event Environment

**Recommendation: Dedicate a session to event preparation two weeks before
the demonstration date. Do not leave this to the week of the event.**

The demonstration event the founder described — 8 to 15 senior aerospace and
finance people, Looking Glass holographic display, executive summary, curated
evening — is a high-stakes environment. The study site will be one of the
surfaces those people interact with. It needs to be polished, fast, and reliable.

Here is what the demonstration environment needs that day-to-day deployment
does not:

**A completed study.** The site must be serving the spaceport study, not the
lunar pathfinder. The spaceport study needs to be substantially complete before
the event date so the site reflects the full analytical work.

**A clean, professional URL.** As discussed above, a custom domain on Vercel Pro.
The URL will be shared in invitations and follow-up materials.

**Offline resilience.** The event venue may have unreliable internet. The site
should be available as a local mirror  a simple `wget --mirror` of the Vercel
deployment stored on a laptop or iPad as backup. This takes fifteen minutes to
prepare and eliminates the risk of a connectivity failure ruining the evening.

**Print-ready executive summary.** The study's executive summary at
`studies/archive/01-orbital-platform/study/00-front-matter/executive-summary.md`
should be rendered as a clean PDF for physical distribution. This is separate from
the Vercel deployment but belongs in the event preparation checklist.

**Pre-event walkthrough.** One week before the event, load the live site on the
Looking Glass display and walk through the full presentation flow. Identify any
rendering issues, missing charts, or broken navigation. Fix them before the night.

## 6. Infrastructure Not Recommended at This Stage

I want to be direct about what I am not recommending and why, because some of
these are standard recommendations that other developers would make reflexively.

**Dedicated cloud server (AWS EC2, Google Cloud, DigitalOcean VPS):** Not needed.
The orchestration engine runs locally. The study site is static and served by
Vercel. There is no persistent process that needs a server. Deploying one would
cost $20–100/month and require ongoing maintenance for no benefit.

**Container orchestration (Docker, Kubernetes):** Premature by years. The system
is a Python CLI tool. Containerising it adds complexity without adding capability
at this stage. If the system evolves to have multiple concurrent users or a web
API surface, reconsider then.

**Separate database hosting (Supabase, PlanetScale, Neon):** The cross-coupling
database and assumption registry are YAML files stored in the repo. This is the
correct architectural decision — documented in ADR-003 — because it gives the
team git-native versioning, diff visibility, and zero infrastructure cost. A
hosted database adds a dependency for no benefit in a system where the database
has one writer (the orchestrator) and is not accessed concurrently.

**Separate API layer:** There is no API in this system. Agents communicate through
the file system. Adding an API layer would be building for a future architecture
that has not been decided yet.

## 8. Recommended Action Sequence

These should be executed in this order. Each step is independent but the sequence
minimises the risk of deploying something broken to the live URL.

**This week:**

1. Fix `assumption_registry.yaml` — add `entries: []`. Commit and push.
   CI goes green. Takes five minutes.

2. Clean up `.env.example` — the file currently lists environment variables
   for services that are not part of this system. Remove everything except
   `ANTHROPIC_API_KEY`. This prevents confusion for anyone who clones the repo.

3. Add `vercel.json` to repo root. Commit and push.
   This wires up the study site deployment without affecting anything live yet.

**After founder approval:**

4. Upgrade Vercel project to Pro plan.

5. Register custom domain and connect to Vercel project.

6. Change Vercel production branch to the space program branch.

7. Trigger deployment. Verify the lunar pathfinder study site loads correctly
   at the custom domain.

**Two weeks before demonstration event:**

8. Confirm spaceport study content is substantially complete.

9. Update `vercel.json` to point at spaceport study output directory.

10. Deploy and do a full walkthrough on the Looking Glass display.

11. Prepare offline mirror and print-ready executive summary PDF.
